### 1.2 五个最贵的教训

1. **永远先验证「桥是否在」**（E-01）：`window.bridge` 不存在时，页面不会报错、按钮不会响应、状态永远初始态。任何 Electron 项目第一件事就是断言 bridge 可用，且**不要用 try/catch 静默吞掉初始化失败**。
2. **静默是最大的敌人**（I-02 / S-04 / D-08）：`canRun` 静默 return、认不出模型静默改投第一个、失败静默兜底——用户看到的都是「点了没反应」或「结果不对」，排查成本极高。任何被拦下的动作都要给出人话原因。
3. **同一个符号不能有两种含义**（U-10 / D-08 / U-11）：`images` 既表示「生成」又表示「识别」、`—` 既表示「未公开」又表示「不适用」、`count=0` 既表示「清空」又表示「无改动」——每次都引发了用户困惑。一个符号一个语义，超出就拆字段。
4. **口径要在三处对齐**（U-11 / D-02）：列表显示名、写入配置名、详情弹窗名，三处任一处不一致，用户就会问「是不是 bug」。三路来源共写一份配置时，统计也必须按来源分家。
5. **验证工具本身会骗人**（C-05 / C-06 / Q-01）：隐藏窗口的定时器节流、`&` 后台进程被 shell 杀掉、陈旧断言、CDP 合成事件触发不了原生拖拽——都曾让我把测试方法的问题当成产品缺陷。**先怀疑验证手段，再怀疑代码**。

## 2. Electron 壳层：进程、模块格式、preload（E）

### E-01 preload 从未被加载（致命，三页同时"卡住"）
- **现象**：页面永远停在初始态（阶段=启动中、0 模型），所有按钮点击发不出动作，三个接入页同时卡住，控制台无报错。
- **根因**：`package.json` 有 `"type": "module"`，electron-vite 把 preload 输出成 `out/preload/index.mjs`，而 `BrowserWindow` 仍指向 `../preload/index.js`（文件不存在）；更关键的是 `sandbox: true` 下 Electron 的预加载脚本**不能是 ESM**，改成 `.mjs` 也加载不了。结果 `window.bridge` 不存在，而 `useService` 里 `window.bridge.onState(...)` 被 try/catch **静默吞掉**。
- **解决**：`electron.vite.config.ts` 的 preload 显式 `output.format: 'cjs'` + `entryFileNames: '[name].cjs'`；`main/index.ts` 指向 `../preload/index.cjs`（产物 `require("electron")`）。
- **防再犯**：窗口创建后第一件事在 DevTools 里断言 `typeof window.bridge === 'object'`；bridge 初始化失败必须 `console.error`，不许空 catch。
- **位置**：`electron.vite.config.ts`、`src/main/index.ts`、`src/renderer/src/composables/useService.ts`

### E-02 服务层 esbuild 纯 ESM 动态 require 崩溃
- **现象**：安装包能装、界面能开，但后台服务 fork 后立即崩溃：`Error: Dynamic require of "node:assert" is not supported`（undici 内部）。此前所有「打包成功」其实都是服务不可用的空壳，因为一直没真正启动过应用。
- **根因**：`build:service` 用 esbuild CLI 打成纯 ESM，undici（CJS）内部 `require("node:assert")` 落到 esbuild 的 `__require` shim，纯 ESM 作用域没有 `require`。
- **解决**：新增 `scripts/build-service.mjs`（esbuild **JS API** + `banner.js` 注入 `import { createRequire } from 'node:module'; const require = createRequire(import.meta.url);`）。用 JS API 而非 CLI `--banner` 是为了避开 Windows cmd.exe / npm script 的引号解析差异。
- **防再犯**：打包完成后必须**实际启动一次应用**并确认服务端口监听，不能只看到 exe 生成就算交付。
- **位置**：`scripts/build-service.mjs`、`package.json`（`build:service`）

### E-03 `ELECTRON_RUN_AS_NODE` 环境变量污染
- **现象**：`electron .` / `npm run dev` 全部崩在 `TypeError: Cannot read properties of undefined (reading 'exports')`；最小 6 行 ESM 应用同样复现，极易误判成「项目 ESM 主进程写坏了」。曾据此把 main 改成 CJS 输出，确认是环境问题后全部还原。
- **根因**：本会话 shell 从宿主继承了 `ELECTRON_RUN_AS_NODE=1`，Electron 被当成纯 Node 启动。
- **解决**：跑 Electron 前一律 `env -u ELECTRON_RUN_AS_NODE ./node_modules/electron/dist/electron.exe .`。
- **防再犯**：先用最小 ESM 应用复现，能复现就是环境不是代码；不要基于环境故障去重构构建配置。
- **位置**：启动命令（非源码）

### E-04 共享类型只能写「可擦除」TS 语法
- **现象**：Node `--experimental-strip-types` 加载服务层/测试时报错。
- **根因**：`src/shared/types.ts` 被主进程、preload、渲染层、服务层、测试共用；若写 `enum` / `namespace` / 装饰器这类需要 emit 的语法，strip-types 无法直接加载。
- **解决**：接口单一真源只用 type/interface + 字符串字面量联合类型；服务层内部 import 一律带显式 `.ts` 扩展名（兼顾 esbuild 与 Node）。
- **防再犯**：新增共享类型时自问「这行会不会生成 JS」。
- **位置**：`src/shared/types.ts`、`package.json`（`test` 脚本带 `--experimental-strip-types`）

### E-05 主进程不打包服务层，构建顺序有依赖
- **现象**：dev/build 起来后服务进程找不到 `out/service/main.mjs`。
- **根因**：服务层由 esbuild 单独打包，electron-vite 不 bundle 它。
- **解决**：`dev` / `build` 脚本都前置 `build:service`。
- **防再犯**：改 npm scripts 时不要删这条前置依赖。
- **位置**：`package.json`、`electron.vite.config.ts`

### E-06 单实例锁让第二个实例秒退
- **现象**：想再起一个带 `--remote-debugging-port` 的验证实例，进程 1 秒退出、exit code 0、日志只有 `DevTools listening`、无任何报错，CDP 端口连不上。
- **根因**：`app.requestSingleInstanceLock()` —— 用户自己的 dev 已在运行，第二个实例直接 `app.quit()`，并把 `second-instance` 信号发给已有窗口。
- **解决**：不要和用户的 dev 抢；必要时用独立 `--user-data-dir` 起第二个实例（但要注意服务端口冲突）。
- **防再犯**：起验证实例前先 `netstat` 看 31280/31282 是否被占；端口被占说明已有实例在跑。
- **补充（23:05 实测）**：`requestSingleInstanceLock()` 在 `app.setPath('userData', dataDir)` **之前**执行，所以给第二个实例设独立的 `MOBRIDGE_DATA_DIR` 也绕不过锁——锁仍基于默认 userData，照样 1 秒 exit 0。想同时跑两个实例必须把 `setPath` 提到锁之前，或临时停用锁（别为了验证改产品代码）。
- **位置**：`src/main/index.ts`（requestSingleInstanceLock）

### E-07 「关窗 = 退出」的隐性数据副作用
- **现象**：点 × 关窗后，写入目标客户端里的模型配置被清空；关闭时还会卡死几秒。
- **根因**：`shutdown()` 里调了 `syncPublished([])` —— 退出被当成了「移除」，清空了用户配置；且每个 await 无超时，探测/写盘挂住就卡死。
- **解决**：退出**不再**同步空集合，摘条目只由 `/admin/remove` 触发；每个 await 用 `settle(work, ms)` 加超时（运行时 2.5s / 探测 2s / 写盘 2s…）；主进程 `stopService` 宽限 20s→8s，`before-quit` 加 20s 看门狗 `app.exit(0)`。实测关闭→全退 2–4s。
- **防再犯**：任何生命周期钩子里的「写配置」动作都要问：这是用户主动要求的吗？退出路径只做清理不做业务写入。
- **位置**：`src/service/core/main.ts`（shutdown）、`src/main/index.ts`

### E-08 服务启停是主进程职责，动作要绕过 ready 闸门
- **现象**：服务停止后无法再启动（动作被 `phase !== 'ready'` 拦掉）。
- **根因**：`service-stop` / `service-start` 属于子进程生命周期，归主进程；若放进通用动作派发，会被「服务未就绪」闸门一律拒绝。
- **解决**：加进 ACTIONS 白名单，并在 `phase !== 'ready'` 判断**之前**单独处理；stop 直接置 `phase:'stopped'` 并清空 endpoint/pid/probe，start 校验 `phase==='stopped'` 后置 `starting` 再 `startService()`。
- **防再犯**：新增管理类动作时先判断它属于「服务内部能力」还是「进程生命周期」。
- **位置**：`src/main/index.ts`（ACTIONS / action handler）、`src/renderer/src/composables/useService.ts`

### E-09 外链安全四道闸
- **现象/风险**：Electron 窗口承载远端内容 = 安全风险；官网链接又必须能唤起系统浏览器。
- **解决**：① `setWindowOpenHandler` 一律 `{action:'deny'}`；② `will-navigate` 一律 `preventDefault()`；③ 页面按钮走显式 `open-external` IPC；④ 服务端 `isAllowedExternal()` 精确匹配 `EXTERNAL_HOSTS` 且限 `https:`，其余拒绝返回 `{ok:false}`。
- **防再犯**：新增「官网 ↗」链接时，必须同步把域名加进白名单——`test/external-links.test.js` 已把这个对应关系锁死（Q-04）。注意 `isAllowedExternal` 返回 `URL.toString()` 规范化结果（裸域名会补结尾斜杠）。
- **位置**：`src/shared/constants.ts`、`src/main/index.ts`、`src/preload/`、`test/external-links.test.js`

### E-10 渲染↔主进程只有两条通道
- **设计取舍**：`onState` 状态广播（~500ms）+ 白名单 `action`。所有跨进程能力都要走这两条，禁止渲染层直接 `require('electron')`。
- **防再犯**：新功能先看能不能用现有 `ServiceState` 字段表达；加字段就改 `src/shared/types.ts` 单一真源，三方同步。
- **位置**：`src/shared/types.ts`、`src/preload/`、`src/renderer/src/composables/useService.ts`

## 3. 窗口与标题栏 WCO（W）

### W-01 合并标题栏后拖拽 / 双击最大化失效
- **现象**：把原生标题栏并入接入行后，按住空白处拖不动窗口、双击也不能最大化。
- **根因**：`.app-header` 有 `-webkit-app-region: drag`，但 no-drag 名单里写的是 **`.app-tabs` 整个容器**；该容器 `flex: 1 1 auto` 撑满头部中段，用户眼里的「标题栏空白处」几乎全被它盖住 → 整片中段被豁免。
- **解决**：no-drag 从容器收窄到具体控件：`.app-tab, .theme-control, .notice-root, .svc-toggle, .settings-btn, .status-cluster`。容器不声明即整块可拖，页签按钮挖洞后仍可点。
- **防再犯**：见 W-02 区域算法；CSS 注释已写红线。
- **位置**：`src/renderer/src/App.vue`

### W-02 `-webkit-app-region` 的区域算法（必背）
- 规则：`drag` 矩形**整块生效**，只有显式声明 `no-drag` 的后代才会从中「挖洞」；后代默认 `none` 不会挖洞。所以 no-drag 必须只声明到**具体控件**，绝不能盖住一个会用 flex 撑满的容器。
- 双击最大化与拖动都依赖同一套非客户区命中判定，两者会一起失效、一起恢复。
- **防再犯**：改头部布局后，用 `elementFromPoint(x,20)` 沿祖先链检查样本点有没有 no-drag（本次实测 x=560 空白可拖、x=615 状态簇不可拖）。

### W-03 WCO 主题同步
- **方案**：`titleBarStyle: 'hidden'` + `titleBarOverlay: {color, symbolColor, height: 52}`；`nativeTheme.on('updated')` 里 `window.setTitleBarOverlay({color, symbolColor})`（仅 win32，try/catch）。
- **防再犯**：改主题色板时同步改 `titleBarOverlay` 的 color/symbolColor，否则深色下窗口按钮会看不清。
- **补充（23:36 用户截图抓到）**：`titleBarOverlay.color` 必须与 `.app-header` 的 `--surface` **完全同色**（浅 `#ffffff` / 深 `#242426`）。早期填的是 `--background`（`#f5f5f7` / `#1c1c1e`），比白色顶栏灰一档，右上角 WCO 区域就留下一条肉眼可见的色带——用户看到的「交接处颜色不一样」就是它。初始值与 `nativeTheme` 更新两处必须共用同一个 `titleBarColors()` 函数，否则换主题时又会漂移。

### W-04 `env(titlebar-area-*)` 预留 + 回退
- **方案**：`padding-right: calc(100vw - (env(titlebar-area-x, 0px) + env(titlebar-area-width, 100vw)))`。WCO 生效时实测 136px；不支持 WCO 的环境全部取回退值，算出来是 0，不留白。
- **防再犯**：不要写死 `padding-right: 136px`。

### W-05 header 高度与 `titleBarOverlay.height` 对齐
- **方案**：header `height: 52px` 必须与 `titleBarOverlay.height: 52` 一致，否则原生窗口按钮与内容错位。
- **防再犯**：改顶栏高度时两处一起改。

### W-06 删除「更多」菜单误删开标签 → 用户 dev 白屏
- **现象**：`npm run dev` 直接白屏，Vue 编译报 `Invalid end tag (174:11)`。
- **根因**：大段模板删除时连带删掉了设置按钮的**开标签**，留下孤儿 `</button>`。
- **解决**：恢复 `<button class="settings-btn" …>`；重建后 typecheck + build 干净。
- **防再犯**：**任何模板结构性删改后立即跑 `vue-tsc` + `npm run build`**，不要等用户启动 dev 才发现。同时检查与 UI 改动绑定的文案（`phaseText()` 里「⋯ 更多」的旧措辞就漏改了）。
- **位置**：`src/renderer/src/App.vue`

## 4. 打包、安装与本机环境（B）

### B-01 winCodeSign 解压失败
- **现象**：7za `-snld` 还原包内 macOS 符号链接时普通用户无权限，exit 2；electron-builder 判缓存失效后重下，Go 下载器直连 GitHub 超时。
- **解决**：`--config.win.signAndEditExecutable=false`（已核对 25.1.8 的 winPackager.js / nsisUtil.js 均短路），或开 Windows 开发者模式 + `ELECTRON_BUILDER_BINARIES_MIRROR`。代价：exe 无自定义图标/版本元数据。

### B-02 `app.asar` 被常驻进程锁住（最顽固）
- **现象**：`EnsureEmptyDir` 删不掉 `release/win-unpacked/resources/app.asar`，标准 `npm run build:win` 反复失败。
- **根因（实测）**：只有 `resources/app.asar` 被锁（同目录 188MB 的 exe、resources.pak 全 FREE）；三个 `release*` 目录的 asar 全 LOCKED；把同一个 asar 复制到 node_modules / 项目根 / TEMP 三个副本全 FREE —— 说明是**打包过程中被某个常驻扫描进程打开后持续持有**，不是「文件一存在就被扫」。嫌疑：Defender / 360 / Everything / SearchIndexer。
- **解决**：`scripts/build-win.mjs` 每次生成 `release-<时间戳>` **全新且尚不存在的目录**、注入 npmmirror 镜像、默认带 `signAndEditExecutable=false`；`package.json` 加 `build:pack`。输出路径字符串用**正斜杠**；脚本用 `process.execPath` 直接执行 `node_modules/electron-builder/cli.js`，不依赖 npx/shell。
- **防再犯**：**「换输出目录」必须每次一个全新目录名**，复用同一个 `release2` 第二次必定失败。`.gitignore` 用通配 `release*/`。
- **彻底根治（需用户在系统侧做）**：把项目目录加入 Defender/360 排除项 + 开启开发者模式，之后可直接 `npm run build:win` 且保留图标。

### B-03 electron postinstall 超时 + @electron/get 缓存布局
- **现象**：`npm install` 最后一步直连 GitHub 下载 electron 二进制超时，npm 回滚导致 `node_modules` 只剩 `.bin`。
- **解决**：缓存根 `C:\Users\jz\AppData\Local\electron\Cache`，命中路径 `<root>/<sha256(下载目录 URL，不含文件名)>/electron-v<版本>-win32-x64.zip`；把已有 zip 复制到对应哈希目录即可零下载命中。实测用户自行 install 37s 完成、无下载记录。

### B-04 npm registry 证书误判
- **现象**：curl 报 `CERT_HAS_EXPIRED`，据此外推「npm 拉不动」。
- **根因**：用户 `.npmrc` 有 `strict-ssl=false`，npm 根本不校验证书，浏览器与 npm 都正常。**curl 的现象不能外推到 npm**。用户已切 `registry.npmmirror.com`。

### B-05 Windows 下 bash 花括号展开生成畸形空目录
- **现象**：磁盘上出现 `src/renderer/{src/`，内含 `assets}` / `components}` 等 5 个空目录；用户感觉「目录是乱的」。
- **根因**：初始化用 `mkdir -p src/renderer/{a,b,c}`，PowerShell/cmd **不展开花括号**，被当字面字符；随后又用正确路径重建了真目录。空目录 git 不跟踪，`git status` 完全看不到，易长期残留。
- **解决**：删除畸形树；`scripts/rasterize-icons.mjs` 把输出目标收拢成显式清单；README 新增「目录约定」+ PowerShell 自查命令。
- **防再犯**：路径逐条写全，或用 `fs.mkdirSync(path, { recursive: true })`。

### B-06 源 / 生成物边界
- `resources/*.svg` 是图标**唯一真源**；`resources/tray*.png`、`build/icon*.png` 由 `npm run icons` 生成但**入库**（打包时不再依赖 Chrome）；`out/`、`release*/`、`dist/`、`node_modules/` 是生成物，不手工放文件；临时截图放 `os.tmpdir()` 带 pid 并 `try/finally` 清理。
- `src/renderer/index.html` + `src/renderer/src/` 是 electron-vite 双层约定，**不是重复目录**。

### B-07 GUI 进程在非交互会话秒退
- **现象**：通过工具 `Start-Process` 启动的 GUI 进程数秒内 ExitCode=0，连 status.json 都不生成。
- **根因**：工具会话 / 非交互桌面无法保持 Electron 窗口常驻，不是应用问题。
- **解决**：桌面端验证请用户自行双击 exe；自动化验证走 CDP（见 §10）。

### B-08 IDEA / 固定 output 目录
- IDEA run config 用了 `directories.output: release` 固定目录，与 B-02 同源失败；应改用 `npm run build:pack`（时间戳目录）。

## 5. 渲染层 UI / CSS / Naive UI（U）

### U-01 未定义的 CSS 变量让浅色表头变黑
- **现象**：亮色主题下表格表头一片深色。
- **根因**：`ModelTable.vue` 写 `var(--table-heading, #2c2c30)`，而 `global.css` 亮/暗两套都没定义 `--table-heading` → 永远退回深色兜底值。
- **解决**：亮色补 `#eceef3`、暗色补 `#2c2c30`。
- **防再犯**：新增 `var(--x, fallback)` 时，两套管子里都要有 `--x`；兜底值会掩盖漏定义。

### U-02 Naive 深色默认按钮 = 灰色实心块
- **现象**：深色下「检测全部 / 检测选中 / 只勾选可用」像灰色实心芯片，与顶栏描边按钮两副气质。
- **根因**：Naive 深色默认按钮自带 `rgba(255,255,255,.08)` 半透明白底。
- **解决**：深色主题 overrides 给 `Button` 注入 `color: transparent` + `border: 1px solid rgba(255,255,255,.30)`（hover .50），以及 colorHover/Pressed/Focus 一套。

### U-03 边框测量陷阱（导致误判修复没生效）
- **坑**：Naive 按钮的**可视边框画在子元素 `.n-button__border` 上**。读按钮本体的 `borderTopColor` 会读到文本色（rgba .82），看起来像「覆盖没生效」。
- **解决**：测子元素，或直接读按钮上的 `--n-border` CSS 变量。
- **防再犯**：用组件库时先确认视觉属性落在哪个 DOM 节点，不要凭直觉测根元素。

### U-04 浅色默认按钮同样的填充问题
- **现象**：浅色下「只勾选可用 / 全部取消」仍是浅灰实心底，和「设置」按钮（透明 + 描边）不一致。
- **解决**：浅色也注入同族覆盖，取值直接抄 CSS 变量：`color: transparent`、`colorHover #f0f4fa(--hover)`、`border 1px solid #d8d8dd(--line)`、`borderHover #61616a(--muted)`、`textColor #61616a` / hover `#242426(--text)` / disabled `#9a9aa2`。primary 不受影响，仍是唯一实心强调。
- **防再犯**：主题覆盖必须**深浅成对**做，只做深色会在另一半主题复发。

### U-05 液态玻璃「没效果」
- **根因**：`backdrop-filter` 作用在纯平底色上等于什么都没做，看上去就是一张白卡。
- **解决**：新增 `.app-ambient` 氛围层（三团错开的径向渐变冷色光斑，右列专配两团）；玻璃 bg alpha 降到 .46/.22；`blur(26px) saturate(185%)`；内容层 z-index 在氛围层之上。
- **防再犯**：玻璃要有「可透的东西」，先有背景层次再谈毛玻璃。

### U-06 `.plan { min-height: 100% }` 导致整页滚动
- **现象**：行高跟着表格内容一起长，整页滚动、卡片压住内容。
- **解决**：`height: 100%; min-height: 0`，表格才在内部滚动（实测 bodyScroll 808 = client 808）。

### U-07 说明文字被挤成半行
- **解决**：`.pane > * { flex: 0 0 auto }`，空间不足时别压缩文字。

### U-08 窄窗口右卡布局
- **解决**：≤1180px 时右卡掉到下方，必须 `height: auto; min-height: 100%` 并给卡 `max-width: 460px`（否则 kv 拉满整行）；模型表操作列 11%→15% + nowrap，避免「详情/重测」上下叠两行。

### U-09 数量提示重复
- **现象**：日日新表头「3 已勾选」与工具栏「已勾选 3 个」；OpenCode 表头「0 可用」与底部「已选 0 / 可用 0」。
- **解决**：定规则「**一个数字只出现一次**」——表头只放清单事实（模型/可用/最大上下文），勾选数统一在勾选按钮那一行的工具栏右侧；OpenCode 底部只报「已选 N 个」。AtomCode 表头的「已勾选」是那页唯一计数，保留。
- **防再犯**：新增统计前先找一遍页面上有没有同语义数字。

### U-10 图像列语义混用
- **现象**：`images` 布尔在 `kind='image'` 上表示「图像生成」、在 chat 模型上表示「支持图片输入」，列表都显示「支持」；脚注又说「图像生成模型标不适用」→ 6.8 Flash「支持 + 可用」与 U1.5「支持 + 不适用」看起来自相矛盾。
- **解决**：新增 `imgCell()` 拆成 **生图 / 识图 / —** 三值 + 各自 title；脚注重写；详情弹窗「支持图像: 是/否」→「图像能力」；AtomCode 同列统一（其 `images` 来自 `supports_vision`，纯识图）。
- **防再犯**：一个布尔跨两种实体类型时，展示层必须按类型拆开，不能共用一个标签。

### U-11 三页名称口径不一致
- **现象**：「AtomCode 有 AC 标识，OpenCode 和日日新没有」。
- **根因**：三路写入客户端的名字**都有** `OC ·` / `AC ·` / `SN ·` 前缀，但 AtomCode 列表主名直接用了写入名，另两页显示官方名/真名，写入名藏在详情或写入预览里。
- **解决**：统一「**主名 = 写入客户端名，副名 = 官方名 / 上游真名**」；三页「模型」表头加 title 说明前缀用途、脚注补「三路来源前缀防同名互踩」；OpenCode 详情弹窗补「写入客户端名」行。
- **防再犯**：列表显示名、写入配置名、详情弹窗名三处必须同时核对。

### U-12 卡片间「色带」
- 右列两张 `.glass` 卡之间的大投影叠出一条明显色带。解决：去掉大投影，只留 1px 边线 + 内高光，缝隙回到页面底色。

### U-13 通知 4 秒消失看不到历史
- **现象**：用户倒杯水回来就看不到「刚才写入成功没」「那句英文报错写的什么」。
- **解决**：`NotificationCenter.vue` 铃铛 + 未读徽标 + 历史面板 + 详情弹窗；localStorage `mobridge-notices` 上限 200，打开即已读、可清空。

### U-14 结果类反馈不该改动布局
- 原先提示条插在页面顶部，一出现就把内容整体顶下去。改右下角浮层（4.2s/8s 自动消失、可关闭、最多 4 条；循环进度用 `note(text, kind, {stream})` 复用同一条不刷屏）。

### U-15 按钮禁用原因只挂 title
- **现象**：用户点下去只觉得「没反应」。
- **解决**：`WriteCard.vue` 按钮下方**常显**一行写不进去的原因；破坏性操作先确认弹窗；长内容走弹窗。反馈分层：结果=页面提示条（不打断）、破坏性=先确认、长内容=弹窗。

### U-16 托盘图标一张静态图，总有一边看不清
- **现象**：托盘/任务栏小图标只有一张静态 PNG——深色任务栏下深色线条图标几乎隐形，浅色任务栏下浅色图标同样消失。且 Windows 的**桌面/开始菜单大图标不随系统主题切换**，能随主题变的只有托盘。
- **根因**：托盘图标渲染在系统任务栏上，底色由用户主题决定；应用侧若不监听主题，就只能选一头。
- **解决**：托盘出**日夜两版**（`resources/tray-icon-day.svg` 浓墨线条 / `tray-icon-night.svg` 霓青线条 → `tray-day.png`/`tray-night.png`，走既有 `npm run icons` 管线）；`src/main/tray.ts` 按 `nativeTheme.shouldUseDarkColors` 选版，并在 `nativeTheme.on('updated')` 里 `tray.setImage()` 重建，重建前判 `tray.isDestroyed()` 防退出期崩溃；macOS 例外——必须用纯黑模板图标（`trayTemplate.png` + `setTemplateImage(true)`），系统自动反转，**不许带彩色点缀**。
- **防再犯**：凡是「画在系统底色上」的资产（托盘、通知图标、快捷方式大图标）都要问一句：系统底色是深还是浅？谁负责切换？macOS 是否要求单色模板？三问没答案就别交付单一版本。
- **位置**：`resources/tray-icon-{day,night,template}.svg`、`scripts/rasterize-icons.mjs` ASSETS、`src/main/tray.ts`。

## 6. 主题三态（T）

### T-01 持久化与系统模式
- `system/dark/light` 三态存在 localStorage `mobridge-theme`；系统模式跟主进程 `nativeTheme`（`window.bridge.setThemeSource` / `onNativeThemeChanged`）；`apply()` 直接切 `documentElement.classList`，`isDark` 是 computed，主题 overrides 与 WCO 颜色都是它的下游。
- **防再犯**：所有视觉相关配置都以 `isDark` 为单一来源，别再各自读 `matchMedia`。

### T-02 「主题切换延迟 600ms」是假象
- **现象**：CDP 测出浅色补丁比深色慢 600ms+，差点当成响应 bug；`setTimeout` 采样脚本甚至被拖到 SIGTERM。
- **根因**：**隐藏/后台窗口的定时器被 Chromium 强节流**；CDP 合成事件也不会走原生非客户区命中测试。
- **解决**：用 `MutationObserver`（微任务级、不受节流）+ `Page.bringToFront` 实测——htmlClass 与全部 29 个按钮 style 在**同一毫秒**批量落盘（25ms / 829ms），补丁本来就是即时的。
- **防再犯**：测「补丁何时生效」一律用 MutationObserver，别用 setTimeout 采样；测原生拖拽/最大化不能靠 CDP 合成事件。

### T-03 覆盖必须深浅成对
- 见 U-02 / U-04。只在一半主题注入 overrides，另一半必然复发。

## 7. 服务层：网络 / 探测 / 转发（S）

### S-01 首启「卡住」的真因
- **现象**：页面停在「检测模型」数分钟，只有一条静态文案、零进度。
- **根因（硬数据）**：本机无 OpenCode 运行时，首启必须下载平台包 `opencode-windows-x64@1.19.5`，content-length **79,636,104 字节 ≈ 75.9 MB**，解压出 211 MB 的 exe。干净数据目录复测是 21 秒下完、25 秒进 ready，所以不是「永久卡死」，是**没有信息**。
- **附带**：`registry.npmjs.org` 元数据 2.2s / `registry.npmmirror.com` 0.2s，原代码把官方源排首位。

### S-02 下载三件套
- `runtime.ts`：① `streamTo()` 按 600ms 节流上报「百分比（已下/总量 MB，MB/s）」；② 镜像优先 `['npmmirror','npmjs']`，但 integrity 仍取官方 metadata，镜像被篡改依然拦得住；③ 停滞看门狗 `STALL_TIMEOUT=25s`（2 秒粒度判断「多久没收到新数据」，超时 abort 换源），总时长 180s 上限保留（慢但一直在动不算停滞）。
- **防再犯**：任何超过 3 秒的操作都要有阶段 + 进度，不能只有一句静态文案。

### S-03 额度用完被记成「超时」（一轮耗掉 4 分钟）
- **现象**：12 个模型各等 60 秒，整轮 4 分钟「检测中」，最后全记 `timeout`。
- **根因**：本地 OpenCode 服务收到上游 429 后**自己退避重试**，重试事件里带着上游原话 `Free usage exceeded, subscribe to Go`；`probeOneModel` 不接这个信号，只能等 60 秒超时。
- **解决**：`meta.activity` 接住 `session.status.retry` 的 message；命中额度类正则就 `abort()` 当场收手，记为 429 `rate_limited` 并把上游原话作为原因。实测整轮 7 秒结束（11 个 quota、1 个 access）。
- **防再犯**：超时是「没收到答案」，不是「收到了拒绝」；上游明确拒绝必须单独归类。

### S-04 转发口认不出模型时静默改投 `models[0]`
- **现象**：用户选 A 实际跑 B，且无任何提示。
- **解决**：改为 404 `model_not_found` 并列出可用模型。
- **防再犯**：**兜底到第一个元素**是危险默认值，宁可报错。

### S-05 写入配置的 id 与转发口匹配口径不一致
- **现象**：写进墨坊/DSH 的 `models[].id` 是上游真名，而转发口只按 `AC · xxx` 匹配 → 必然走兜底。
- **解决**：三处写入统一用展示名 `AC · xxx`，转发口同时容忍真名（兼容旧配置/手写配置）。
- **防再犯**：写入侧与读取侧的名字映射必须有测试锁住（`test/atomcode-bridge.test.js`）。

### S-06 探测期间切不了写入目标（最长 4 分钟锁）
- **根因**：`setTarget` 守卫含 `probing`，一整轮最坏 60s×12/并发3。
- **解决**：允许探测期间切换，并发安全靠 ① `syncWrites` 串行 ② 先切内存 `state.target` 再清理旧目标（清理期间排进来的写入会落到新目标）；清理失败把内存目标退回去，避免内存比落盘跑得更前。

### S-07 超大请求体收不到 413
- **根因**：`readBody` 在 `for await` 里抛错会销毁请求流，客户端只看到连接断开。
- **解决**：先看 `content-length` 预判，超限时 `req.resume()` 丢掉剩余字节再抛，客户端能正常收到 413。

### S-08 `atomcode --version` 解析到 Windows 代码页警告
- **现象**：页面显示「已检测到 AtomCode Console code pages…」。
- **根因**：Windows 上先把代码页警告打到 stderr，`run()` 合并 stdout+stderr 后取第一行。
- **解决**：`pickVersion()` 跳过警告行只取 `x.y.z`；且「能跑起来就算装上」，认不出版本不再判成未安装。

### S-09 默认端口不能沿用旧项目号段
- 旧产品 41980/41982，墨桥改为 **31280 / 31282**（主端口 +2），避免撞号与「两者还连着」的误解；设置面板可改，改完自动重启服务。`deriveAtomcodePort()` 是唯一推导规则。

### S-10 两个转发口语义不同，不能合并
- OpenCode 需要信封协议 + 工具调用翻译；AtomCode 需要注入 `X-AtomCode-Sig/Ts/Nonce/Alg/Ver` 等头 + token；日日新客户端能直连，**不需要转发口**。判断规则是「客户端能否自己直连上游」。

### S-11 系统代理与 URL 细节
- 只认手动配置的 HTTP/HTTPS 代理，PAC 与 SOCKS 拿不到可用转发口就**直接报错**，不猜地址；IPv6 字面量进 URL 必须加方括号，否则被当成端口分隔符。

### S-12 运行时二进制与环境
- `.cmd/.bat/.ps1` 启动脚本不能当运行时二进制（Windows `spawn` 判 EINVAL、文本冒充 exe 是 UNKNOWN），要拒绝并记录原因；已是目标版本的托管文件不要重写（Windows 无法替换正在运行的映像）；环境变量按白名单复制，别的 provider 的 key 与授权覆盖都不带进来。

### S-13 信封协议 / 探测纯度
- 信封有三种抵达方式（结构化字段 / 已完成的 StructuredOutput 调用 / 纯文本），只读第一和第三曾把一次正确答案判成格式错误；**检测路径永远不翻译**，探测必须量模型本身而不是量翻译的功劳；语义没命中是一次随机事件，重试一次（格式失败与超时不重试）。

### S-14 AbortSignal 错误不要透传
- 抛的是不透明的 `The operation was aborted`，直接透传会被记成不明原因错误；超时判定由探测自己持有。

### S-15 探测缓存与「一次性观察」分开
- 判定与某次真实调用的观察必须分开记，混在一起一次上游抽风就会把模型从可用列表撤掉；失败按「当时负载」(10 分钟) 与「关于模型的结论」(1 小时) 分级 TTL。
- **相关回归**：采用缓存判定后，可用清单必须用**合并后的结果表**算；旧写法读上一份 `modelResults`，会漏掉刚采用成功的模型（`test/model-status.test.js` 锁住）。

### S-16 全不可用时的诊断横幅
- 12 个模型里 11 个 `Free usage exceeded`、1 个地区限制，0 可用——这是上游额度耗尽，不是本机配置错。页面按错误原文分组计数并明说「不是本机配置写错了」，避免用户以为程序坏了。

### S-17 平台二进制名不能写死
- Windows 是 `opencode-windows-x64` / `opencode.exe`；测试写死 darwin 那对会让整条 Windows 路径压根没被测到。

### S-18 测试假响应必须带 `headers`
- 下载进度靠 `content-length` 算百分比，少这层会让测试走成「无长度」分支，和线上行为不一致。

### S-19 进度语义（已解决）
- 早期探测队列只有 `active/pending`、没有「还剩几个」；现由 `OpProgress.vue` 底部常驻条（label + `3/12 · 模型名` + 计时 + 进度轨，数据来自 `useService.currentOp`）解决。

## 8. 配置写入与数据安全（D）

### D-01 owner 必须按来源分家
- **风险**：三路模型写进同一份 `models.json`，共用一个 owner 标记会让任一路把另外两路的条目当成「旧条目」擦掉。
- **解决**：`SOURCE_OWNERS = { opencode:'mobridge-v1', atomcode:'mobridge-atomcode-v1', sensenova:'mobridge-sensenova-v1' }`，`mergeModels/syncModels` 全部参数化；DSH patch 里每个来源占一个 provider 键。
- **兼容**：早期版本标记写在 `buddyBridgeOwner`，读取时一并认，旧条目下次写入自动换成新字段。

### D-02 「移除配置」看着能点却摘不掉
- **现象**：OpenCode 页显示「已写入 2 个」，点移除什么也没发生。
- **根因**：`inspectTargets()` 用 `OWNERS = Object.values(SOURCE_OWNERS)` 统计，把**日日新**写进 WorkBuddy 的 2 条算成了 OpenCode 的；而 `syncPublished([])` 只摘本线 owner。
- **解决**：`TargetInspection.sources` 按来源分家——WorkBuddy 按条目 `mobridgeOwner` 分桶，DSH/墨坊按 provider-id 前缀（`mobridge` / `mobridge-atomcode` / `mobridge-sensenova`，**最长前缀优先**）；渲染层 `sourceSliceOf()` 统一按线取数，配置卡补一句「同一份配置里还有 日日新 的 2 条，那不是本页写的」。

### D-03 前缀匹配最长优先
- `mobridge` 是 `mobridge-atomcode` 的前缀，短前缀先匹配会把另外两路算到 OpenCode 头上。所有前缀分类必须按长度降序。

### D-04 墨坊（jzWorkBuddy）配置的三条铁律
- 只增删带 owner 的那一条 provider，**绝不改 `activeProvider`**（那是用户当前用哪家的选择）；已有同 id `mobridge` 时返回 `conflict` 不覆盖；数据目录必须与它自己的「新 `~/.mofang` 优先、旧 `~/.ai-coding-tool` 沿用」规则一致，否则会写进一个应用根本不读的目录。

### D-05 DSH patch 是「按 id 整段替换」
- 必须把 provider 合并进已有的 `llm-pi-ai`；追加第二条会把用户其它 provider 整段顶掉。

### D-06 原子写与备份
- 写前备份 + `pruneBackups` + 原子替换 + 二次读比对；内容相同直接返回不写不备份；读写之间文件被别人改过就整体放弃重来；`atomic.ts` 处理 Windows rename 被占用要重试，`json.ts` 兼容 BOM。

### D-07 空集合覆盖风险（**未完全关闭**）
- 全不可用时自动 `syncPublished([])` 会以空集合覆盖写入目标（allowEmpty），可能清掉此前写入的条目。已有测试守卫「空清单只有允许时才写入」，但**建议后续区分「自动同步」与「用户点移除」**——自动同步永远不许清空。

### D-08 `sync.count = 0` 有两种语义
- 真清空（`changed: true`）vs 启动空同步（`changed: false`）。抽 `syncCountText()` 统一为 `N 个` / `无改动` / `已清空`，状态面板、环境弹窗、配置卡三处共用；0 条时标题改叫「最近同步」。

### D-09 切换写入目标先摘旧条目
- 否则两处配置都指向本机转发口，关掉 MoBridge 后留下两份死配置。

### D-10 写入安全总原则
- owner 覆盖式同步 + 二次确认；移除只摘自己条目、不动其它工具配置；`workbuddy-config.ts` 里记过/显式指定的路径**不能悄悄回退**到另一个 profile，找不到就返回 null 由调用方决定。

### D-11 设置是不可信输入
- `domain/settings.ts` 的 `normalizeSettings` / `pickKnownKeys`：缺字段、多字段、写成字符串、写进 null 都要归一成一份能用的完整设置；可调项从各处硬编码收敛到一处；探测 TTL 支持 `configure()` 热改 + `clear()`。

### D-12 安装命令固定白名单
- 不拼接任何用户输入，也不用 `curl|sh` / `irm|iex` 这类管道脚本（见 P-04）。

### D-13 写入目标路径预设，用户搬目录就写错地方
- **现象**：WorkBuddy / DSH / 墨坊的配置目录被用户搬家后，墨桥仍按固定目录或环境变量找配置，模型写进一份客户端根本不读的文件；界面也不显示「当前写到哪」。
- **根因**：WorkBuddy 虽有 `workBuddyModelsFile` 持久化 + 自动查找/手动选择，入口却只在**托盘菜单和导入弹窗**，设置面板完全看不到；`dshHome` 是模块级常量（启动时算一次，只认 `DSH_HOME` / `~/.dsh`），墨坊 `resolveMofangConfig()` 只认 `MOFANG_HOME` / 两个固定候选。三者没有统一的「可见、可改」入口。
- **解决**：
  1. 设置面板新增「写入位置」分组，三目标各显示**当前实际路径 + 定位状态 + 是否手动指定**，提供 `自动查找`（WorkBuddy）/`更改…`/`恢复默认`；换位置先内联确认（破坏性操作）。
  2. 键名/形态常量下沉 `src/shared/target-path-keys.ts` 三方共用——**渲染层不能直接引服务层模块**，会把 `node:fs` 拉进浏览器包。
  3. 优先级 **设置 > 环境变量 > 默认目录**；服务层 `validateTargetPath()` 保存前校验（文件名必须是 `models.json`、DSH 目录须含 `profiles/`、墨坊 JSON 须含 `providers`），找不到就明确报错，**绝不静默回退**。
  4. 换路径前 `cleanupOldPaths()` 按三路 owner / provider 前缀从旧位置摘掉墨桥条目，再切运行时、落盘、重新体检，并按当前目标重新写入；落盘失败回滚运行时快照。
  5. 只读 `auto-locate-path` 动作只给路径、不触发写入（区别于老的 `find-config`，它会顺手 import）。
  6. **实测返工**：WorkBuddy 的「自动查找」最初直接调 `findConfig()`，它依赖 OpenCode runtime 起一个只读模型会话做跨盘 glob，隔离环境里 **60 秒都没返回**（服务状态卡在「正在只读查找 WorkBuddy 配置…」），按钮像死了一样。改成 `locateWorkbuddyFile()` 纯本地 stat 扫常见位置 + 各盘符用户目录，实测 **9ms** 返回；dsh/墨坊各 3ms。设置面板里依赖模型的重查找一律禁止。
- **防再犯**：任何「写进别人配置文件」的功能，必须同时给 ① 当前路径可见 ② 可改 ③ 找不到时明确报错；换位置属于破坏性操作，先确认再从旧位置清理。**设置面板里的按钮必须是毫秒级响应**，不要挂到模型/网络链路上。`test/target-paths.test.js` 锁住归一化、优先级、三种形态校验与本地定位。
- **位置**：`src/shared/target-path-keys.ts`、`src/service/config/target-paths.ts`、`src/service/core/main.ts`（saveSettings / describeTargetPaths / cleanupOldPaths / applyTargetPaths / autoLocatePath）、`src/main/index.ts`（pick-target-path）、`src/renderer/src/components/SettingsModal.vue`

## 9. 交互与状态口径（I）

### I-01 乐观更新 + 门禁读同一份状态 → 目标永远切不了
- **现象**：点 DSH / 墨坊提示「已经是当前写入目标」，无法切换（我上一批改出来的回归）。
- **根因**：`runAction` 先乐观更新 `state.target`，`blockedReason('target')` 又拿同一份状态比对，必然相等。
- **解决**：门禁不再比对此值（幂等由服务端负责），点击当前目标直接忽略不弹提示。

### I-02 `canRun` 静默 return → 「点了没反应」
- **解决**：`blockedReason(name, value)` 返回人话原因，`run()` 被拦时把原因作为 `error` 返回 → 各页 catch 用 toast 弹出；同名动作放行（`pendingLocal === name`），避免 `pushBusy('remove')` + `run('remove')` 互锁。
- **另一根因**：按钮当时在右栏、步骤 3 是空的，用户根本点不到 → 三步并两步 + 写入动作放进当前步骤。

### I-03 `refresh()` 置 `reading` 把用户打回第 1 步
- `connectDone` 原来只认 `ready`；`ServicePhase` 补 `reading`，新增 `serviceUsable()`。

### I-04 步骤乱跳 / 步骤可达条件
- `active` 默认跟随 `currentStep`，但**用户手动回看旧步骤时不再把他拽回来**；第 2 步可达条件用「有没有 Key」而不是「验没验证过」（否则刚存完 Key 会被锁在第 1 步，而验证按钮在第 2 步）。

### I-05 错误提示中英混杂
- 新建 `src/shared/failure.ts` 纯函数：把 CLI/上游原文翻成「一句中文结论 + 一句下一步做什么」，原文进通知详情；`test/failure.test.js` 9 例锁住（含 MobaXterm 那段原文）。抽成纯函数是为了可测，不要在 Vue 组件里堆正则。

### I-06 状态口径诚实
- `—` = 上游未公开，**不编造**；耗时 = 完整请求用时（非首字延迟）；缓存判定明确标注「非本次实发请求」；上下文是官方声明值非实测；不可用模型仅在本窗口保留、不供客户端使用。

### I-07 反馈分层
- 结果 = 页面提示条（不打断）；破坏性操作（写入/移除）= 先确认弹窗再反馈；长内容 = 弹窗。参考 U-13/U-14/U-15。

### I-08 日日新自动鉴权
- `saveKey()` 成功后自动 `validate()`；`onMounted` 时若已存 Key 且未 validated 自动补一次（`autoValidated` 标记，一会话一次）。

### I-09 设置弹窗的输入保护
- 状态广播（~500ms）不能盖掉用户正在敲的字（防抖 + 局部状态）；超时设置别调太小，否则把「慢」误判成「不可用」。

### I-10 文案与 UI 改动同步
- 移除「更多」菜单后，`phaseText()` 的停止文案仍写「右上『⋯ 更多』→『启动本地服务』」，属于 stale 文案。UI 结构调整后 grep 一遍旧措辞。

### I-11 目标体检必须现读
- 切页签就 `inspectTargets()`：用户可能刚在别的工具里改过配置，「移除配置」能不能点必须按此刻事实算，不能沿用上次结论。

### I-12 目录快照与「可用」分开
- 清单是官方文档静态快照（官方无动态模型目录接口），「可用」是发真实请求量出来的；图像模型走 `/images/generations`，不发文本探测，状态标「不适用」而非「不可用」——「没测」不等于「坏了」。

## 10. CDP / 验证方法论（C）

### C-01 隐藏窗口截图会挂住
- 窗口最小化/隐藏时页面不开帧，`Page.captureScreenshot` **直接超时**（表现为卡住而不是报错）。必须先 `Page.setWebLifecycleState {state:'active'}` + `Emulation.setFocusEmulationEnabled({enabled:true})`。

### C-02 「幽灵点击」
- 宽泛文本匹配（`button,a,div` 里找文字）会命中包裹层 div，把页签/主题点乱，曾误判成「主题切不动」。**一律用精确类名选择器**：`.app-tab` / `.theme-btn` / `.rail-btn` / `.tc-switch button`。

### C-03 `location.reload()` 不生效
- 经 `Runtime.evaluate` 发 `location.reload()` 后页面仍挂旧 bundle（脚本 hash 不变）。必须 `Page.reload { ignoreCache: true }`；`.tmp-verify/cdp.mjs` 已加 `reload` 模式。

### C-04 合成事件触发不了原生拖拽 / 最大化
- `Input.dispatchMouseEvent` 绕过 Electron 的 `WM_NCHITTEST` 非客户区判定，双击与拖动都不生效。这类行为只能请用户手动确认；自动化可验证的是**区域判定**（elementFromPoint + 沿祖先链查 no-drag，见 W-05）。

### C-05 setTimeout 采样被节流
- 隐藏窗口里 50ms 的 setTimeout 会被拖到数百毫秒，甚至把采样脚本拖到 SIGTERM，制造「补丁延迟」假象。用 `MutationObserver` + `Page.bringToFront`，见 T-02。

### C-06 测试方法本身制造假象
- 用 `&` 后台起进程，shell 结束时连带杀掉 → 误判「下载停滞、AbortSignal 不生效」。改用受管后台任务复测，结论是 21 秒下完。**先怀疑验证手段，再怀疑代码**。

### C-07 临时改代码验证后必须还原
- 为截第 3 步图曾临时把 `StepRail.reachable()` 改 true，**截完立刻还原并重建**。任何「为了验证而改的产品代码」都要登记并复原。

### C-08 验证实例与用户 dev 抢锁
- 见 E-06。`.tmp-verify/` 是 CDP 截图与调试脚本目录，已加 `.gitignore`。

## 12. 协作红线（P，非技术但会翻车）

| 编号 | 规则 |
| --- | --- |
